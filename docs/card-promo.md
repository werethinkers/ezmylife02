# Visiting-card gift (5,000 promo credits)

A printed 90 × 55 mm card carries a QR to `ezyourlife.com/card/<CODE>`. The person scans it, creates an
account (or logs in), and 5,000 gift credits are added to that account. Once per account.

## Rules (all enforced in the database, `20261025100000_card_promos.sql`)

- **Gift credits are a third bucket**, `credit_wallets.promo_balance`. A run is paid with gift credits first,
  then free credits, then bought credits.
- **3 uses per app.** Gift credits can pay for an app at most `promo_per_app_limit` times (3). A use is one
  successful run that took any gift credits, counted in `promo_app_uses`. After that the app needs free or
  bought credits. This is what bounds the AI cost of a card.
- **Bulk Mode** goes through the same `start_tool_run` / `complete_tool_run`, so each file is one use.
  `bulk-run` and `productvision-angles` add `promoRunsAffordable()` to their up-front "can you afford it" check.
- **Developer apps (`dev-*`) never take gift credits.** Their money goes to the developer.
- **One card claim per account** (`card_promo_claims.user_id` is unique), so cards cannot be stacked.
- **Unique cards** (`kind = 'unique'`) work once in total. **Shared cards** (`kind = 'shared'`) have one code on every
  card; each account still claims once, and `max_claims` can cap the total.
- **Expiry is optional** (`expires_at`, "Claim by"). It stops new claims; credits already claimed stay.

## Admin: Admin → Growth → Gift cards

1. **Make cards**: a batch of unique codes (up to 2,000) or one shared code. Set credits, uses per app, label,
   optional claim-by date.
2. **Design and sign**: name, title, line on the card, and signature (draw with finger/mouse, or upload a photo of a
   signature on paper). The signature and wording are saved in this browser only.
3. **Preview and print**: front and back preview, PNG download, and A4 print (10 per sheet, fronts then backs
   mirrored for double-sided printing).

## Going live

Same as everything else (`docs/launch-plan.md`): the website needs Publish in Lovable, the SQL must be run through
the Lovable database connection, and `claim-card-promo` is a new server function. `src/integrations/supabase/types.ts`
is regenerated by Lovable; until then the new columns are read untyped.

## Not covered

`mail-desk` still checks `free + paid` for its "enough credits" preview, so a person with only gift credits sees
"not enough" there even though the charge itself would use gift credits.

## Nothing hidden from search or categories

`npm run check:discoverable` fails if an app or design sits in no category that belongs to a goal, or has no words for
search to match. Lists (`/ai-apps` and the home list) also add a last "More apps" section for apps whose category has no
goal (for example a category made in admin without one), so those are never dropped.
